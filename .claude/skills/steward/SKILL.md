# Stewarding PRs in ban_allowlist

This is a Home Assistant custom integration. Read this before acting on CI
failures or review comments on a PR here — it saves re-discovering the same
dead ends every time.

## Running checks locally

```
./uv venv
./uv pip install --python .venv/bin/python -r requirements.test
.venv/bin/pip install tzdata   # needed for the test suite's US/Pacific fixture; not in requirements.test
PYTHONPATH=. .venv/bin/pytest -vvv          # mirrors .github/workflows/unittest.yaml
.venv/bin/pre-commit run -a                 # mirrors .github/workflows/pre-commit.yaml
```

`pre-commit run -a` runs black, flake8, isort, a few generic hooks, yamlfmt,
and `make mypy` (`MYPYPATH=stubs .venv/bin/dmypy run .`) in that order — a
failure log only shows hooks up to and including the first failing one only
if an earlier hook errors out entirely; usually all hooks run and each
reports its own pass/fail.

**Python version matters for mypy.** This repo pins Python 3.12
(`.python-version`, and `actions/setup-python` in every workflow). If your
local `python3` is older, mypy will report false positives from
version-gated stdlib APIs — e.g. `Path.walk()` (added in 3.12) in
`integration_tests/test_banning_works.py`. Before treating a mypy finding
there as real, re-check with `mypy --python-version 3.12 .`.

Integration tests (`integration_tests/test_banning_works.py`) need a real
Docker daemon and pull a full `ghcr.io/home-assistant/home-assistant` image
per HA version in the matrix generated by `.github/get_versions.py` — they
cannot run in a sandbox without `dockerd`. If you can't reproduce a matrix
failure locally, get the job log via CI instead of guessing.

## CI quirks that look like regressions but usually aren't

- **The integration_tests matrix runs 9+ legs in parallel with the default
  `fail-fast: true`.** One leg timing out cancels the rest before they even
  start, so "8 legs cancelled, 1 failed" is not evidence those 8 would have
  failed too — re-run the whole matrix before concluding anything from a
  fail-fast cascade.
- **`wait_for_http`'s timeout in `test_banning_works.py` needs real margin**
  for a cold `ghcr.io/home-assistant/home-assistant` image pull plus HA's
  full s6-overlay boot in CI. If matrix legs fail with
  `TimeoutError: Waited too long for the port 8123 ...` on more than one
  HA version, or on a version that passed before, that's this timeout, not
  a `docker-compose` or HA-version regression — don't chase the wrong cause.
- **`pytest-homeassistant-custom-component` pins how new a `homeassistant`
  this repo can actually test against.** The resolved `requirements.test`
  lockfile currently sits on `homeassistant==2024.3.3`, well below the
  manifest's stated minimum (`2025.12.0`) — that's not a stale lockfile you
  can fix by re-running `uv pip compile`, it's the newest `homeassistant`
  version `pytest-homeassistant-custom-component`'s latest release
  supports. Consequence: **write config-flow code so it works on the
  pinned test version too**, not only the newest HA API. Concretely, use
  `self.hass.config_entries.async_get_entry(self.handler)` to fetch the
  current entry inside an `OptionsFlow`, not `self.config_entry` (missing
  on `OptionsFlow` before HA added it as a cached property) — the former
  works on every HA version and is what HA's own base class uses
  internally (see `_async_abort_entries_match` in `config_entries.py`).
- **Hassfest's translation schema is strict and undocumented in-repo.** A
  step under `config.step.*` or `options.step.*` in `strings.json` /
  `translations/*.json` only accepts `title`, `description`, `data`,
  `data_description`, `menu_options`, `menu_option_descriptions`, `submit`,
  `sections` — nothing else. A homegrown "pick one of these" screen must be
  `self.async_show_menu(step_id=..., menu_options=[...])` with the option
  labels under `menu_options` in the translation files, not a `vol.In`
  selector with made-up keys like `action_options` — hassfest will reject
  the latter with an unhelpful "did you mean 'menu_options'?" error.
- **`stubs/voluptuous.pyi` is a small hand-maintained stub**, not the real
  package's types (HA depends on the old, unstubbed `voluptuous==0.13.1`).
  If mypy reports a real `voluptuous` API as missing or wrong, check the
  actually-installed library's signature
  (`python -c "import voluptuous as vol, inspect; print(inspect.signature(vol.X.__init__))"`)
  before editing the stub — don't guess.

## The one thing that's actually not fixable from a PR

**HACS validation fails on two repository *settings*, not code**: no
repository topics, and Issues disabled. These live in the repo's GitHub
Settings (General → Topics; General → Features → Issues), and no tool
available to an agent working PRs can change them. Flag it once in a PR
comment and move on — don't keep re-diagnosing it on every CI event, and
don't widen a feature PR to try to work around it.

## Other conventions

- `strings.json` is what Home Assistant shows before translations for the
  user's language have downloaded — keep its wording in sync with
  `translations/en.json` whenever either changes. Hassfest's schema check
  only catches structural violations, not wording drift between the two.
- When bumping a pinned version (a GitHub Action, `docker-compose`, a
  dependency), verify the target version is real by checking that
  project's actual GitHub tags/releases page directly — don't trust a web
  search's summary of release notes, which has been observed to
  hallucinate version numbers and dates.
